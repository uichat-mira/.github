# Mira「向外走」计划

> Status: Working Draft  
> This document is a discussion draft, not Organization policy, not an engineering work-item contract, and not a delivery commitment.

## 为什么现在讨论这件事

Mira 已经有持续发展的 Desktop、Mobile、Agent、官网、GitHub Organization 与公开写作，但目前绝大多数建设和维护仍集中在极少数人身上。

因此，下一阶段除了继续做产品，也需要让 Mira 更稳定地出现在外部世界里，让陌生人逐渐能够：

1. 看见 Mira；
2. 理解 Mira 在做什么；
3. 相信项目会持续存在；
4. 愿意继续关注；
5. 最终让其中一些人愿意使用、讨论，甚至参与建设。

暂时把这件事叫做「向外走」。它不是增长 KPI，也不是一次集中宣传活动。

## 当前判断

现阶段不应该急着大规模招募贡献者。

更合理的顺序是：

```text
被看见
→ 被理解
→ 看到连续更新
→ 建立可信度
→ 开始关注或使用
→ 愿意靠近
→ 参与贡献
```

第一阶段最重要的结果，是让第一次遇见 Mira 的人翻过几页之后产生一个朴素判断：

> 这个项目是真的，而且还在持续往前走。

## 内容原则

Mira 不为了“该发东西了”而制造内容。

先发生，再记录，再分发。

可公开内容主要来自真实建设过程：

- 产品与版本变化；
- Desktop / Mobile / Agent 的真实进展；
- 产品判断与工程取舍；
- 值得记录的失败与修改；
- 开发现场；
- 关于个人 AI 的长期思考；
- Mira 与 Tomz 的写作。

不同渠道可以重新编辑标题、开头和长度，但不应该产生不同版本的事实。

## 渠道草案

### 自有阵地

- `mira.tomz.io`：Mira 的正式公共空间，承载产品介绍、更新、工程现场、长期记录与未来的参与入口。
- `tomz.io`：个人写作与作品空间，让外部读者理解是谁在做 Mira，以及为什么会做出这样的东西。
- GitHub `uichat-mira`：工程真实性来源，展示项目、代码、Release、任务与未来的 Contributor 入口。

### 第一层分发

- Bilibili：主要的新用户发现入口。初期以专栏和动态为主，不强迫视频化。
- 微信公众号：保留已有读者关系，只同步真正值得发布的内容，不承担固定更新压力。

### 技术社区

- V2EX：用于阶段性发布、开源能力、工程故事和有讨论价值的技术/产品取舍。现阶段不作为固定周更渠道。
- GitHub 社区：未来承担从“关注”到“参与”的转换，包括 Contributor 入口、Good First Issue 与清楚的小任务。

### 后续渠道

知乎、即刻、小红书暂时作为候选，不形成固定维护义务。

### 英文世界

Mira 需要英文入口，但不立即进行整站翻译。

第一阶段优先覆盖：

- 英文 Landing Page；
- GitHub Organization / README；
- 一句话定位；
- 核心能力；
- Download / GitHub / Contribute 入口；
- 少数重要更新。

等 Mira 有足够清晰、陌生人可以直接体验的版本后，再考虑 Product Hunt、Show HN、Reddit、X 等渠道。

## 发布节奏草案

这不是硬性日历，目标是形成连续性而不是制造信息噪声。

### 每周

至少留下一个公开痕迹，可以是一条更新、一张截图、一个产品决定、一段开发现场或一篇短札记。

### 每两周左右

尝试形成一篇相对完整的内容，优先沉淀到 Mira 官网，再根据内容改写到 B站或公众号。

### 每月

形成一次轻量的「Mira 最近发生了什么」总结，记录真正完成的事情、方向变化、当前进行中的工作和下一阶段重点。

### 重大节点

新公开版本、明显产品跃迁、重要 Agent 能力、新平台上线、重要开源能力、官网大改版或正式开放贡献时，不等待固定节奏，单独发布。

## 第一批内容候选

1. **Mira 是什么**  
   重新介绍 Mira，讲清楚为什么会有它，以及它和普通聊天客户端有什么不同。

2. **Mira 最近走到哪了**  
   从 Desktop、Mobile、Agent、远程能力中挑已经成立的部分，建立真实进展感。

3. **Mira Mobile 的“双链路”意味着什么**  
   介绍远程桌面能力 + 用户自配 API Key 的产品结构，以及为什么手机端不只是遥控器。

4. **为什么 Mira 不想只做一个聊天框**  
   从工具、Agent、微应用、远程能力等方面解释个人 AI 的产品方向。

5. **一个人维护 Mira，到底在维护什么**  
   展示真实维护面，不卖惨，也为未来的协作者关系建立背景。

6. **Mira 月报 001**  
   尝试建立可持续的公开连续记录。

当前建议顺序：

```text
Mira 是什么
→ Mira 最近走到哪了
→ Mobile 双链路
→ 为什么不只做聊天框
→ 一个人维护 Mira
→ 月度整理
```

## 关于协作者

当前阶段不以“大规模招募”为主题。

理想路径是：

```text
第一次遇见 Mira
→ 觉得有意思
→ 连续看到更新
→ 理解方向
→ 开始使用或讨论
→ 发现自己可以贡献一点东西
→ 第一次贡献
→ 愿意留下
```

真正想找到的不是一次提交很多 PR 的陌生人，而是少数理解 Mira、认同其中一些东西，并愿意长期一起建设的人。

## 暂时不做

- 不购买粉丝或制造虚假数据；
- 不把同一篇文章机械复制到所有平台；
- 不为了运营制造低价值内容；
- 不把 Mira 包装成已经不存在问题的成熟商业产品；
- 不因为“国际化”立即翻译整个网站；
- 不在信任建立之前大规模喊话招募贡献者；
- 不让「向外走」变成维护者新的全职工作。

## 仍待讨论

- 是否开启 GitHub Discussions 作为公开讨论入口；
- Discussion 应该落在 Organization 入口仓库还是其他承载仓库；
- 第一篇正式对外介绍采用什么结构；
- 更新频率是否需要进一步降低；
- 英文 Landing Page 何时进入实际任务；
- 哪些数据值得观察，哪些数据明确不作为 KPI；
- 什么时候开始建设 Contributor Landing 与 Good First Issue。

## 当前阶段

Draft 0 先只解决三个问题：

1. 外部的人能认识 Mira；
2. 外部的人能看到 Mira 仍在持续发生；
3. 外部的人看完以后知道去哪里继续了解我们。

成熟后的具体建设事项，再拆成各自拥有明确 owner、范围与验收方式的小工作项。
